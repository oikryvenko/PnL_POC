1Executive summary

The platform ingests a trade file and daily equity closing prices, validates and versions the trades, and produces daily positions, daily mark-to-market P&L and valuation exceptions. It runs as a six-task Databricks Job over a Bronze → Silver → Gold Delta Lake architecture in the Unity Catalog catalog cibc. Every task writes an audit row, and two Databricks notebooks let users run the Job and review its results.

Centralised trade processing

One Silver row per trade_id, chosen by version, with every rejected record kept in a reject table and a reason.

Market-data integration

Daily unadjusted closes for 10 US tickers from Yahoo Finance (yfinance) with retry and completeness checks.

Data validation

25 trade rules, 8 price rules and duplicate/ambiguity detection. Bad records are quarantined, not dropped.

Trade version control

Highest version wins, then the latest modified_timestamp. An invalid latest version never falls back to an older one.

Lineage

source_file, ingestion_timestamp and Bronze run_id are carried into Silver. Gold rows carry the run that last changed them.

Positions & daily valuation

Cumulative positions on every NYSE session, valued at the exact-date close.

P&L reporting

Daily P&L per date, book and symbol. P&L stays NULL (never 0) when a price is missing.

Exception management

cibc.gold.valuation_breaks records missing prices, missing baselines and unpriced trades per run.

Operational auditability

cibc.gold.pipeline_run_log: one row per task attempt with status, counts and errors.

7.2 Price flow

ingest_prices: resolve tickers and dates → yf.download(auto_adjust=False) with up to 3 attempts (1 s, 2 s backoff) → extract Close → reject the batch if any requested ticker or expected NYSE session is missing → MERGE into bronze.market_prices on (symbol, price_date), updating only rows whose close, currency or source_api changed.

7.3 Trade and Gold flow

process_trades reads the full Bronze trade history, validates 25 rules, selects the latest version per trade_id, merges rejects, MERGEs accepted trades on trade_id, and deletes trade_ids whose latest version is unusable. build_positions and calculate_daily_pnl then recompute the full position and P&L history from Silver and MERGE it into Gold with scoped deletes.

Why two parallel branches. Prices and trades come from independent sources, so ingesting and validating them in parallel shortens the run. A failure in one branch does not stop the other branch from refreshing its Silver table. Gold needs both validated inputs, so build_positions waits for both Silver tasks. If either fails, Gold is skipped and the previous Gold state stays as it was.

Error handling per task. Each main() parses arguments, maps empty strings to “use default”, and calls audit.run_audited_task. That writes STARTED, then SUCCESS or FAILED with error_type and error_message, and re-raises the exception so the Databricks task fails visibly (§22).

Compute. No cluster settings (test-enforced). One serverless environment default_env (client: "2") with dependency ../../dist/*.whl, which the bundle rewrites to the uploaded workspace path. max_concurrent_runs: 1. No task-level retries are configured, so a failed task is retried by repairing the run.

11Data sources

11.1 Market prices

Deviation from the challenge requirementThe challenge names Stooq. The implementation uses Yahoo Finance via yfinance, because the Stooq endpoint returned HTTP 404 in the test environment (tests/live/test_stooq.py). This does not strictly meet the named-provider requirement. The provider is isolated in bronze/ingest_prices.py: Silver and Gold use only symbol, date, close and currency.
  • Tickers: AAPL, TSLA, NFLX, COIN, DIS, MSFT, AMZN, GOOG, META, PLTR (instrument ids INS001–INS010).
  • Range: inclusive start/end. The provider's exclusive end is handled by requesting end + 1 day. A returned date outside the range fails the task.
  • Close: auto_adjust=False gives unadjusted closing prices, stored as strings in Bronze and as DECIMAL(18,6) in Silver.
  • Currency: set to USD by configuration. It is not read from the provider.
  • Holidays / missing prices: only expected NYSE sessions up to today are required. A missing expected (ticker, session) fails the task before writing. NaN closes are skipped and then reported as missing.
  • Connectivity: 3 attempts with exponential backoff. Type and value errors are not retried.
  • Limitations: unofficial API, no SLA, possible rate limits, no corporate-action handling.

12Bronze layer technical design

Bronze stores source data as received, as strings, plus ingestion metadata (source_api/source_file, ingestion_timestamp, run_id). Business validation is left to Silver.

12.1 cibc.bronze.market_prices IMPLEMENTED

Columns: symbol, price_date, close (all STRING), currency, source_api, ingestion_timestamp TIMESTAMP, run_id. The MERGE key is (symbol, price_date). A matched row is updated only when close, currency or source_api differs (null-safe <=>), and the update also replaces ingestion_timestamp and run_id. The previous value survives only in Delta history. The task refuses to run if the target already holds duplicate keys. Inserted, updated and unchanged counts are computed with a join before the MERGE.

12.2 cibc.bronze.trades — historical, insert-only IMPLEMENTED (code) NOT VERIFIED (live)

The current code uses an insert-only Delta MERGE. INSERT OVERWRITE is no longer used. Bronze trades is a historical store of distinct raw records, not a snapshot of the latest file.

RECORD_HASH_SQL = "sha2(to_json(array(trade_id, counterparty_id, ..., modified_timestamp)), 256)"

MERGE INTO cibc.bronze.trades AS target
USING _trade_pipeline_bronze_trades_source AS source
ON target.record_hash = source.record_hash
WHEN NOT MATCHED THEN INSERT (<14 raw columns>, record_hash, source_file, ingestion_timestamp, run_id)
VALUES (source.…)
  • Hash: all 14 raw columns in CSV order. A JSON array keeps NULLs and escapes delimiters, so NULL, empty strings and commas inside values hash differently. Metadata is excluded, so a re-sent file inserts nothing.
  • Duplicates: the batch is deduplicated with dropDuplicates(["record_hash"]) before the MERGE. Records already in Bronze are skipped by the MERGE.
  • Preservation: rows are never updated or deleted, so the original source_file, ingestion_timestamp and run_id are kept. Trades missing from a later file remain.
  • Safety guard: the task fails if any Bronze row has a NULL record_hash, meaning the backfill migration has not been applied.

13Silver layer technical design

13.1 Silver market prices

Typed columns: price_date DATE, close DECIMAL(18,6) NOT NULL. Lineage columns: bronze_run_id, bronze_ingestion_timestamp. Only Bronze rows for the requested tickers and dates are in scope; rows with a blank symbol or an unreadable date are also kept in scope so they can be quarantined. Rejection reasons: NULL_SYMBOL, EMPTY_SYMBOL, INVALID_PRICE_DATE, FUTURE_PRICE_DATE, UNEXPECTED_TRADING_DATE, INVALID_CLOSE, NONPOSITIVE_CLOSE, INVALID_CURRENCY, DUPLICATE_BUSINESS_KEY, AMBIGUOUS_DUPLICATE_KEY. Write: conditional MERGE on (symbol, price_date). Nothing is deleted.

13.2 Silver trades

  • Type casting: try_cast to DECIMAL(18,6), DATE, INT and TIMESTAMP. A failed cast becomes a rejection reason.
  • Required fields: trade, counterparty, instrument and book ids must not be blank.
  • Quantity and price: quantity must be numeric and non-zero, and BUY must not be negative. Price must be > 0. SELL with a positive quantity is negated. SELL with a negative quantity is kept as is.
  • Dates: the trade date must be an NYSE session and not in the future, and must equal the date of trade_timestamp. Settlement must be on or after the trade date and equal the next NYSE session (T+1).
  • Currency: USD only. Instrument/symbol: the instrument must be in the configured map and match its symbol.
  • Reasons are pipe-separated, so one row can carry several reasons.
  • Write: MERGE on trade_id, updating only when a business column changed. Then DELETE of trade_ids whose latest version is unusable. The two statements are not atomic but both are idempotent.

17Trade versioning and deduplication

  1. Exact copies of all 14 raw columns: the first copy is kept and the others are rejected as DUPLICATE_TRADE_VERSION. With insert-only Bronze this now affects only legacy rows.
  2. Rank each trade_id by version DESC, then modified_timestamp DESC.
  3. If the top rank has several different payloads, the trade is ambiguous and every top row is rejected as AMBIGUOUS_TRADE_VERSION.
  4. If the top version is invalid, or any version is unparseable, the trade is unusable and the older valid versions are rejected as SUPERSEDED_BY_INVALID_LATEST_VERSION.
  5. Otherwise the top row is accepted and the older valid versions are rejected as DUPLICATE_TRADE_VERSION.
  6. Trade_ids that appear in Bronze but have no accepted version are deleted from Silver, so they never reach Gold.

18Position calculation

  • Input: every accepted Silver trade (full history, not filtered by Job dates). Signed quantity: BUY > 0, SELL < 0.
  • Daily activity per (trade_date, book, counterparty, instrument, currency): daily_buy_quantity = sum of positive quantities, daily_sell_quantity = sum of absolute negative quantities, daily_net_quantity = signed sum.
  • Timeline: every NYSE session from the first trade date to the later of the last trade date and the last price date, capped at today, plus every trade date. Each position key starts at its first trade date.
  • Closing position = running sum of daily_net_quantity, so positions carry forward on days without trades. The opening position of a day is the previous closing position.
  • Valuation: market_value = closing_position_quantity × closing_price (exact-date close, mapped from instrument_id to symbol through the config map). A missing price gives NULL; quantities are never changed.
  • Historical corrections: the whole history is recomputed each run and MERGEd, so a back-dated correction updates every affected later date. Rows are deleted only for instruments in the source and dates on or after the source's first date.
GapAn instrument that disappears from Silver entirely is outside the delete scope, so its old Gold rows remain and need manual cleanup.

FROM cibc.gold.positions
WHERE valuation_date = (SELECT MAX(valuation_date) FROM cibc.gold.positions)
GROUP BY valuation_date, book_id, instrument_id;

20Data lineage

Tracing a P&L figure back to its sources: (1) Find the daily_pnl row (date, book, symbol). (2) The positions for the same date, book and instrument give the per-counterparty quantities. (3) The trades are silver.trades rows for that book and symbol with trade_date on or before the date. (4) Each trade's bronze_run_id, source_file and bronze_ingestion_timestamp identify the Bronze record. (5) Prices come from silver.market_prices for the symbol and date, with bronze_run_id pointing to the Bronze price row.

Lineage limitsGold tables are aggregates and hold no foreign key to individual trades or prices, so there is no row-level lineage from Gold. Lineage is reconstructed by business keys. Gold run_id marks the run that last changed a row, not the latest run. Bronze price rows keep only the latest value; earlier values are in Delta history.

A. US Equity Market Calendar

Current implementation. src/trade_pipeline/common/market_calendar.py is a lightweight, rule-based NYSE calendar built on pandas AbstractHolidayCalendar and CustomBusinessDay. expected_trading_sessions(start, end) returns sessions in the half-open range [start, end). requested_sessions(start, end, as_of) returns sessions in the inclusive range up to as_of (default date.today()).

It is used more widely than price ingestion and validation: by ingest_prices (expected sessions and missing-price detection), process_prices (UNEXPECTED_TRADING_DATE, completeness), process_trades (NON_TRADING_TRADE_DATE and the T+1 settlement convention) and build_positions (the valuation timeline).

Supported

Excludes Saturdays and Sundays. Excludes New Year's Day, Martin Luther King Jr. Day, Presidents' Day, Good Friday (Easter − 2 days), Memorial Day, Juneteenth (from 2022), Independence Day, Labor Day, Thanksgiving and Christmas. Inclusive ranges. Excludes future dates.

Observance

Fixed-date holidays use nearest_workday: a Saturday holiday moves to Friday, a Sunday holiday moves to Monday.
Assumptions
  1. The solution processes US-listed equities on a simplified NYSE calendar.
  2. A daily close is expected for every regular NYSE session.
  3. The pipeline runs after the US market close. The schedule is 18:00 New York time, two hours after the 16:00 close.
  4. Non-trading days need no closing price. A trade dated on a non-trading day is rejected.
  5. P&L uses the previous available close (latest close before the valuation date) as its baseline. Positions and current-day valuation use only the exact-date close.
LimitationDescription
Simplified calendarCovers recurring holidays but not exceptional NYSE closures (for example national days of mourning or weather events).
Early market closesShortened sessions (such as the day after Thanksgiving) are treated as full sessions. This does not change the result for end-of-day closes but is not modelled.
New Year's observancenearest_workday marks Friday 31 December as a holiday when 1 January falls on a Saturday, although NYSE trades that day. The price for that session would not be expected, and trades dated that day would be rejected as NON_TRADING_TRADE_DATE.
Timezone“Today” is date.today() in the runtime environment, not explicitly America/New_York.
Intraday executionToday's session is expected even before the market closes. A manual run during trading hours fails the completeness check because today's close does not exist yet.
Exchange coverageOne calendar for all instruments. Other exchanges are not supported.
Schedule vs sessionsThe MON-FRI cron also fires on NYSE holidays. A scheduled date is not necessarily a trading day.

Recommended — FUTURE ENHANCEMENT — NOT IMPLEMENTED

  1. Integrate an authoritative exchange-calendar provider.
  2. Choose the calendar per exchange from instrument reference data.
  3. Use timezone-aware market-session calculations.
  4. Support early closes and exceptional holidays.
  5. Check price availability only against completed sessions.
  6. Make the valuation calendar configurable per market.

Design decision. A lightweight calendar keeps the challenge simple, readable and deployable without extra calendar-service dependencies. It is suitable for demonstrating US equity session validation but does not replace an authoritative production exchange calendar.

B. Currency

Current: only USD is accepted. Non-USD prices and trades are rejected (INVALID_CURRENCY). Currency is part of the Gold keys and is stored, but no FX conversion is performed. Prices, trades, positions and P&L are all in USD. Why: challenge scope. Limitation: a currency column alone does not make multi-currency valuation possible. Recommended: currency reference data, FX rates, a base/reporting currency, conversion, FX P&L and currency-specific precision FUTURE ENHANCEMENT — NOT IMPLEMENTED.

C. Instruments

Current: a hard-coded map INSTRUMENT_ID_TO_SYMBOL (INS001→AAPL … INS010→PLTR) in config.py. Silver rejects unknown instruments and symbol mismatches, and Gold maps instrument to symbol for price joins. Limitation: a ticker is not stable reference data. Symbols change and are reused, and they are not unique across exchanges. A code release is needed for every new instrument. Recommended: an instrument master with instrument_id, symbol, exchange, currency, asset class, instrument type, trading calendar, price source, active status and effective dates, so historical trades join to the mapping valid at the time FUTURE ENHANCEMENT — NOT IMPLEMENTED.

D. Counterparties

Current: counterparty_id must not be blank. No reference check, and no active or inactive status. It is part of the position key. Recommended: a counterparty table (id, name, status, country, effective dates) with referential-integrity checks and rules for inactive counterparties FUTURE ENHANCEMENT — NOT IMPLEMENTED.

E. Books

Current: book_id must not be blank. No reference table. Recommended: a book table (book id, name, business unit, base currency, active status) FUTURE ENHANCEMENT — NOT IMPLEMENTED.

F. Trade status and lifecycle

Trade lifecycle processing is not implementedThe schema has no trade status column. A version is a successive record of the same trade, and the highest valid one wins. A status (NEW, AMENDED, CANCELLED, CORRECTED, SETTLED) would describe the business state. Cancellations cannot be expressed: a trade that disappears from a later file stays in Bronze and Silver and keeps counting in positions. Amendments are handled only as new versions.

Recommended: status, amendment, cancellation and reversal events with effective dating. A cancellation would remove the trade's quantity from the trade date onwards and trigger a recompute of the affected position and P&L dates. An amendment would replace quantity or price for its effective range FUTURE ENHANCEMENT — NOT IMPLEMENTED.

G. Trade, settlement and valuation dates

Positions are trade-date based. The settlement date is validated (on or after the trade date, next NYSE session) but does not affect positions, and there is no settlement status. Valuation date is a Gold calendar date (NYSE session or trade date). Modified timestamp only orders versions. Recommended: settlement lifecycle integration with settled vs traded positions FUTURE ENHANCEMENT — NOT IMPLEMENTED.

H. Market prices

Daily unadjusted closing prices (auto_adjust=False) from Yahoo Finance, one source, no price-quality checks beyond positivity and completeness. Splits, dividends and other corporate actions are not applied. Missing exact-date prices produce breaks. Holidays need no prices.
